# AI search

Open **Ask AI** in the rail or View menu, or press **⌘⇧L** (Ctrl⇧L elsewhere; rebindable). From a readable inbox thread, **Ask AI about this thread** adds an explicit context chip. The assistant docks beside the current content; at narrow widths it occupies the content area temporarily. Close it or press Escape to return. Closing cancels active work. Panel width is adjustable and saved.

## Set up and search

1. Connect Slack/Gmail **read access** in [Inbox](inbox.md). A browser pane's cookies are independent of these grants. Other apps remain visible as unavailable for historical search.
2. Choose Codex or Claude Code and **Check runtime**. Hangar discovers the installed CLI through PATH and standard macOS installation locations. It does not install or modify either binary.
3. Sign in through the selected runtime's own browser flow. Codex uses ChatGPT; Claude Code offers its subscription, Console and organization SSO choices. After completing browser sign-in, use **Refresh login status**. No subscription token is copied from your existing coding sessions or entered in Hangar.
4. Review workspace and accounts. Current workspace is the default; select at most eight accounts. The assistant chooses relevant sources within that selection. Include selected-thread context only if wanted and its account is selected.
5. Ask a question and press **Search with Codex/Claude Code**. The text beside this action explains that your question and retrieved source content go to that provider. There is no automatic provider fallback. The selected provider's eligibility, billing and limits apply.

The panel shows search activity, streamed text and source references. Click a numbered source to open its original thread. Sources distinguish a search preview from a thread actually read and show retrieval time. Only IDs issued by Hangar's broker become clickable; model-written URLs and invented source IDs never become navigation commands. Responses remain plain text, including any model Markdown. Follow-ups carry a bounded previous answer only with the same provider and identical account selection, and instruct the runtime to retrieve fresh evidence.

Searches are bounded, not exhaustive: three minutes, 16 tool calls, 12 returned summaries per search, 80 unique evidence records, 100,000 retrieved characters and 50,000 answer characters. Reads include at most 30 messages/18,000 characters. Existing connector limits and upstream rate/retention rules also apply. **Stop search** preserves clearly labelled partial output; **Clear search** discards the answer and evidence. Disconnect/revocation removes derived answers and cancels in-flight work. A current-workspace change clears that workspace's answer; explicit All workspaces remains an all-workspace scope.

## Runtime support and isolation

Compatibility was verified on 18 October 2026 against **Codex CLI 0.163.0** and **Claude Code 2.1.292**. Other versions fail closed until their protocol/tool surface has been checked and the pin updated. CLI auto-updates can therefore require a Hangar compatibility update. Official installation instructions: [Codex CLI](https://developers.openai.com/codex/cli), [Claude Code setup](https://code.claude.com/docs/en/setup).

Profiles live below Hangar's user-data directory at `ai-runtimes/codex` and `ai-runtimes/claude`. Authentication stays with the unmodified runtime, with Codex requesting its OS keyring store. These profiles are separate from your usual coding profiles and excluded from Hangar config export/Git sync. Environment inheritance is allowlisted: unrelated API keys, developer hooks and `NODE_OPTIONS` are not passed through. Provider stdout is parsed as a bounded protocol; stderr and raw auth output are not relayed into Hangar logs. Hangar keeps answers/evidence in memory only. Runtime-owned diagnostics and account state are governed by each CLI; do not treat those profiles as portable config or enable raw protocol logging around private searches.

**Codex:** a supervised `app-server` over stdio, experimental dynamic tools, ephemeral threads, no host skill discovery, no project instructions, approval policy `never`, read-only filesystem sandbox and network-disabled sandbox. Shell/apply-patch, browser/computer, apps/plugins, subagents, memory, hooks, image generation and other unrelated tools are disabled. Effective policy and the returned session's sandbox/instruction sources are checked. Runtime requests other than this thread's dynamic search/read calls are denied. [App-server protocol](https://learn.chatgpt.com/docs/app-server), [configuration](https://learn.chatgpt.com/docs/config-file/config-reference).

**Claude Code:** unmodified `--print` runtime with `--restricted`, all built-in tools disabled, explicit settings, hooks disabled, no session persistence and a strict MCP configuration. The only allowed MCP tools are Hangar search/read; permissions that would prompt are denied. A per-run random bearer token protects a loopback-only MCP endpoint, which rejects browser origins and exposes no file, shell, send, edit or arbitrary URL operation. The runtime's initial tool manifest is checked. `--bare` is deliberately avoided because it disables OAuth/keychain authentication. Administrator-managed runtime policies still apply; conflicting tool surfaces are refused. [CLI options](https://code.claude.com/docs/en/cli-reference), [programmatic operation](https://code.claude.com/docs/en/headless), [unmodified-runtime authentication conditions](https://code.claude.com/docs/en/legal-and-compliance).

## Extending the implementation

`shared/ai.ts` defines renderer DTOs. `main/ai/contracts.ts` defines `AgentEngine`: status, login/logout, run, streamed text/status/evidence, cancellation through an AbortSignal, and disposal. `AiController` fixes workspace/account scope and creates one `SearchBroker` per run. Engines cannot widen scope. Add a future engine through this interface and the provider selector/registry; connectors and the inbox remain unchanged. Direct API engines can use the same broker in process; runtime engines can use the MCP facade. Do not wrap a second agent loop around a runtime that already owns its loop.

Only the owned assistant main frame may invoke `ai:request`; the rail, service pages, inbox and control socket cannot retrieve its transcript. `ShellState` carries only `aiOpen`, not message bodies or answers. IPC arguments, query sizes, account sets and citations are checked in main. Retrieved messages remain untrusted evidence; instructions inside them cannot add capabilities. A new connector implements `ReadConnector` and account authentication, then advertises its actual read/search capabilities through `ConnectorHub`.

## Verification and release checks

`npm run check` covers typechecking, lint, dependency boundaries, broker account denial, prompt-injection capabilities, fabricated references, budgets, cancellation/late output, source revocation, follow-up isolation, authenticated MCP and process exit/oversized output. `npm run test:e2e` exercises the native panel, all rail positions, compact return, real Electron Escape events, sender checks, streaming and citations with synthetic provider/source fixtures, plus light/dark axe checks.

Run `node scripts/probe-ai-runtimes.mjs` on a machine with both pinned CLIs, or add `codex`/`claude` to check one. It creates temporary fresh profiles, supplies synthetic credentials only to **local mock inference endpoints**, asserts the actual advertised tool manifests, and verifies a host tool call, streamed answer and completion. It makes no paid inference calls and uses no real messages. CI does not require installed providers or live accounts.

These checks prove implementation/protocol behavior; they do **not** establish live account eligibility, real Slack/Gmail OAuth approval, cross-app retrieval quality or provider billing. Before beta, complete the registered test-account trial and the [search evaluation](ai-search-evaluation.md). Public OAuth/provider compliance review, replies, full personal Messenger history, saved transcripts, semantic indexing and proactive searches remain outside this release.
